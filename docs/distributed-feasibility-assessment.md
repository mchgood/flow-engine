# 分布式执行可行性评估

- 日期:2026-10-01
- 性质:技术评估,不含实施决策;实施需先做范围变更(requirements 目前明确将分布式调度、持久化执行划在范围外)
- 评估对象:`DefaultFlowEngine`(1015 行,含全部协调逻辑)及 core 依赖层

## 1. 结论

| 诉求 | 可行性 | 路线 | 改动量 |
| --- | --- | --- | --- |
| 多实例高可用部署(每个执行完整落在一个节点) | **可行,低风险** | sticky 执行 + 注册同步(可复用 FlowSource/Nacos) | 新增集群门面模块,引擎零改动 |
| 单流程跨机器执行 / 持久化断点恢复 | **可行但属新项目** | 状态外置 + 事件驱动新 runtime,复用编译层 | 重写 runtime(~1000 行)+ 新增持久化/序列化层 |
| 在 `DefaultFlowEngine` 上原地改造 | **不可行** | 存在 5 项进程内硬假设,详见 §3 | — |

总体判断:**编译层与结果契约具备分布式就绪性,执行层不具备**。正确的演进姿态是"保留 `DefaultFlowEngine` 作为进程内执行内核,分布式能力以独立模块/新引擎形态叠加",而不是原地改造。

## 2. 现状盘点(代码证据)

## 3. 五项硬约束与解法

1. **绑定即不可传输**:解法是分发源码而非编译产物——FlowSource SPI(Nacos)已实现定义分发;各节点用同一 Markdown 本地编译(definitionHash 校验一致性)。
2. **引用传递**:分布式必须引入"边界序列化"(节点入参/出参/祖先结果跨网络时),这是**破坏性语义变更**——对象身份、共享可变对象、性能特征全部改变。需要在 requirements 中重新定义数据可见性契约。
3. **同步 execute**:可保留同步门面(调用方阻塞等待远程终态),但流程期限到期后调用方与集群的裁决需要显式协议(当前是同一把锁内的即时裁决)。
4. **取消与物理退出**:替换为租约心跳 + 取消令牌;"物理退出才释放额度"的精确语义退化为"租约过期视为死亡",`physicalExitUnconfirmed` 字段的含义需要重定义。
5. **容量语义**:准入与 in-flight 记账需外置(全局配额服务)或按"执行归属节点"分片,嵌套祖先链记账(-1/+1 沿父链)在跨节点子流程下需要分布式事务或弱化。

## 4. 候选方案对比

### 方案 C:多实例 sticky 部署(每个执行完整落在一个节点)

- 形态:新增 `flow-engine-cluster` 门面(注册同步 + 执行路由 + 健康检查);`DefaultFlowEngine` 每节点一个,执行全程不出节点
- 复用:100%(引擎、FlowSource、拦截器全部原样)
- 语义:零破坏;缺点是节点故障丢在途执行(无恢复)
- 工作量:**约 1-2 周**;风险低
- 适合:高可用、水平扩吞吐(按执行分片)

### 方案 D:抽取事件接缝(为分布式铺路,仍是单机)

- 形态:把 `success/fail/settle` 的内部回调重构为可插拔的事件通道(节点完成事件出、命令入),协调泵改为可由外部驱动
- 复用:编译层 + 大部分运行时;改动集中在 `DefaultFlowEngine` 内部接缝
- 语义:单机语义不变;收益是方案 B/A 的前置工程
- 工作量:**约 2-4 周**;风险中(泵循环与锁耦合紧,35 个运行时测试是安全网)
- 适合:确定要走分布式、想分步降险

### 方案 B:事件溯源 + 主备协调器

- 形态:节点完成事件持久化(事件日志),协调器带租约选主,故障切换后重放恢复;执行仍整体归属一个协调者,worker 拉取 TASK
- 语义:取消/超时弱化为租约级;引用传递必须先解决(见 §3-2)——这是本方案的隐藏大头
- 工作量:**约 2-3 个月**;需持久化层、序列化契约、requirements 范围变更
- 适合:持久化断点恢复

### 方案 A:全分布式(队列 worker + 外置状态)

- 形态:Temporal 式——外置状态存储 + 任务队列 + 无状态 worker 池;跨机器执行单个流程
- 语义:§3 全部五项都触发,尤其数据模型(序列化)是产品级破坏
- 工作量:**3-6 个月以上**,建议作为独立项目而非对现有框架的演进
- 适合:单流程需要跨机弹性、长时流程(小时/天级)

## 5. 若实施,必须先完成的范围变更

1. requirements.md:重新定义数据模型(序列化边界)、取消/超时语义、容量语义;FR-11 的同步 execute 语义保留方式
2. AGENTS.md:项目范围声明调整(分布式调度/持久化执行出栈)
3. 新模块边界:`flow-engine-cluster` 或 `flow-engine-runtime-distributed`,契约仍不依赖实现

## 6. 建议

1. **先确认诉求**(高可用部署 vs 持久化恢复 vs 跨机弹性),三者成本差一个数量级
2. 高可用诉求 → 直接做方案 C,现有 SPI(Nacos FlowSource)已铺好定义分发,无需动 core
3. 持久化/跨机诉求 → 先做方案 D 的接缝抽取作为独立里程碑,验证 35 个运行时测试全绿后再立分布式项目
4. 任何路线都不应修改 `DefaultFlowEngine` 的对外契约——它是进程内核,也是分布式节点的执行单元
